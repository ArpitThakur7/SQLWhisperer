🔄 Autonomous Self-Healing State Machine

When validation fails, SQL execution encounters a database error, or the result inspector flags suspicious row counts, SQLWhisperer does not crash. It injects diagnostic failure context into the next iteration: 

[User Query] ──► Schema Retrieval + Semantic Rules + Few-Shot Memory
     │
     ▼
[Attempt 1: Text2SQL] ──► Generated SQL Query
     │
     ├─► [Validation Check] ──(Syntax / Hallucination Error)──┐
     │         │                                             │
     │         ▼ (Valid)                                     │
     ├─► [AST & DB Execution] ─(Runtime DB Failure)──────────┤
     │         │                                             │
     │         ▼ (Success)                                   │
     ├─► [Result Inspector] ──(Empty set / Out-of-bounds)────┤
     │         │                                             │
     │         ▼ (Satisfactory)                              ▼
     ▼                                           [Error Stack Recorded]
[Business Explainer & Audit DB]                              │
     │                                                       ▼
     └───────────────────────────────────► [Attempt 2: Text2SQL with Diagnostics]
                                          (Prompt includes failed queries & fixes)

🛡️ AST-Level Deterministic Guardrails

SQL injection defense goes far beyond basic regex. SQLWhisperer parses the Abstract Syntax Tree using sqlglot:

1️⃣
Root Node Verification
Every statement root MUST be an instance of exp.Select. Multiple statements or stacked queries (e.g. SELECT 1; DROP TABLE...) are rejected immediately.
2️⃣
Recursive Sub-Tree Walking
Walks every branch of the syntax tree to ensure nested subqueries do not hide mutations (e.g. exp.Insert, exp.Delete, exp.Drop, exp.Alter).
3️⃣
Restricted Table Interceptor
Scans table tokens in the AST against settings.blocked_tables to safeguard internal schemas, credentials, and sensitive audit records.
